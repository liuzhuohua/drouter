## 一、问题清单（按严重程度分级）

### P0 · 用户能直接撞上的功能故障（已全部修复）

| # | 页面 | 现象 | 根因 | 处理 |
|---|---|---|---|---|
| 1 | 网卡与桥接 / LAN 口 | 点「应用」弹 **未知的模块：system** | `system` 是纯配置模块，只入库、没有渲染器 | helper 新增 `CONFIG_ONLY_MODULES`，返回明确提示；前端不再把它送进 apply |
| 2 | WAN 口 | 点「应用」弹 **未知的模块：pppoe** | 渲染器叫 `ppp`，`ALIASES` 里缺 `pppoe→ppp` | 补别名 + `APPLY_SPEC` 条目，现在能真正渲染 PPPoE peers 与 chap-secrets |
| 3 | 端口转发 / DMZ | 点「应用」先弹 **未知的模块：portfwd**，再应用防火墙 | `portfwd` 是纯配置模块，规则是注入 `nft_v4/nft_v6` 一起渲染的 | 改为「保存 portfwd → 应用 nft_v4+nft_v6」两步，顺序不再颠倒 |
| 4 | VLAN / WOL / QoS / DPI / PPPoE 多拨 | 点「保存」弹「当前页面无需保存配置」、点「应用」报未知的模块 | 这些页有自己的页内按钮，却错误地显示了全局动作条 | 移除 `needSave`；动作条改由 `PAGE_MODULES` 决定是否显示 |

### P1 · 静默失效（不报错，但功能其实没干活）（已全部修复）

| # | 位置 | 现象 | 根因 |
|---|---|---|---|
| 5 | NTP 时间同步 | 点「应用」永远显示成功，但 **chrony 配置从未做过语法检查** | `_verify()` 按 `module == 'chrony'` 分支，前端传的是别名 `ntp`，永远匹配不上。`upnp`（→miniupnpd）同理 |
| 6 | 修复 #5 后暴露 | NTP 应用报 `Could not open ... : Permission denied` | Debian 的 AppArmor profile `usr.sbin.chronyd` 只放行 `/etc/chrony/**` 与 `/etc/chrony.*`，校验文件放在 `/tmp`、`/run` 下 root 也会被拒 |
| 7 | 全部配置模块 | 快照静默漏掉整个 `/etc/drouter`（上一轮已修） | `rescue.conf` 0600 root 读不到 → `shutil.copytree` 整体抛异常 → 界面仍显示「已创建快照」 |

**#5/#6 的修法**：新增 `render.canonical()`，`act_apply` 先解析成渲染模块名再传给
`_verify()` 和 nft 重载；新增 `VERIFY_PATH['chrony'] = '/etc/chrony.drouter-verify.conf'`；
预检目录从 0700 的 `/run/drouter-helper/verify` 换成 0755 的 `/run/drouter-verify`
（radvd 这类降权读配置的守护需要能 traverse 进来）。

### P2 · 性能（第 7 项，已完成）

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 14 个接口串行总耗时（模拟刷一遍全站） | 8977 ms | **581 ms**（≈15×） |
| 热态中位耗时 | 608 ms | **24 ms** |
| `/api/ulog` | 2799 ms | **118 ms** |
| `/api/vlan` | 598 ms | **5 ms** |
| `/api/theme` | 524 ms | **6 ms** |
| `/api/storage` | 608 ms | **13 ms** |
| `/api/ifaces` | 688 ms | **45 ms** |
| `/api/ulog` 响应体 | 298 KB | 压缩后 13.2 KB（4.4%） |
| `app.js` | 437 KB | 压缩后 126 KB（28.9%） |

**四项优化**
1. 常驻执行守护 `drouter-helpd`：原来每个请求 spawn 一次 `sudo python3 helper`
   （实测 236 ms 固定开销），改为 Unix socket 常驻，只 import 一次；socket 连不上
   自动回退 subprocess，并带 30 秒「守护不可用」冷却，不会每个请求白等。
2. `conntrack -E` 是阻塞事件流，原来固定 `timeout 2` 让每次查询白等 2 秒；
   改为默认走内核日志，只有勾选「抓实时连接事件」时才订阅。
3. 响应 gzip 压缩（带 mtime+size 键的内存缓存）+ ETag/304 协商缓存，
   并补上 `Vary: Accept-Encoding`（否则代理会把 gzip 喂给不支持的客户端）。
4. 两个守护不再共用 systemd `RuntimeDirectory` —— 它会让一个守护重启时
   把另一个的 socket 一起删掉，表现为「shelld 显示 active 但终端废了」。

## 四、可以上生产了吗

**代码层面可以。** 上面 P0 / P1 七项全部修复并有测试兜底，性能达到目标。

上生产前还需要你确认两件事（涉及网络切换，我没有擅自执行）：

1. **当前这台机器还没有接管路由**：`ip_forward=0`、默认网关仍是 192.168.7.2
   （远端 CHR RouterOS）、`nft list ruleset` 为空。它现在只是局域网里的一台普通
   主机。真正切换需要先规划停机窗口。
2. **建议先在构建保护模式下走一遍**：创建 `/etc/drouter/BUILD_MODE` →
   在各配置页点「应用」只会写盘不启服务 → 用只读预览核对生成的
   `/etc/dnsmasq.d/drouter.conf`、`/etc/nftables.d/drouter-v4.nft` 等文件 →
   确认无误后再关闭保护模式、正式接管。
