# Debian 13 主路由系统 —— 优化版项目规格与架构设计

> 本文是对原始 13 条大白话需求的工程化重写，并吸收四份参考方案的精华、剔除其弊端。  
> 可直接作为后续开发/交付给任意 AI 的项目提示词使用。

## 一、目标机实测现状（2026-09-27 重新采集，192.168.7.3 / PVE 102）

> 本机曾装有第三方路由系统 `landscape-router`（占用 DNS:53、DHCP:67 等），  
> 因影响局域网，用户已用 ZSDT 快照还原 Debian 13 至干净状态。  
> 以下为**还原后**的实测现状。

| 项目               | 实测值                                                                                 | 影响                |
| ---------------- | ----------------------------------------------------------------------------------- | ----------------- |
| 系统               | Debian GNU/Linux 13 (trixie)，内核 6.12.107-amd64                                      | 符合底座要求            |
| 引导               | SeaBIOS 传统 BIOS（无 /sys/firmware/efi）                                                | 符合要求，grub-pc      |
| CPU / 内存         | 2 核 / 3.9 GiB（可用 3.2 GiB）                                                           | 必须极致轻量            |
| 桌面               | xfce4 + xserver-xorg + lightdm **已安装**                                              | 满足 RealVNC 前提     |
| **RealVNC**      | **`realvnc-vnc-server 6.11.0.47988` 已安装并在运行**（`vncserver-x11-serviced`，监听 5900）     | ✅ 关键变化，见 §5.1     |
| 物理网卡             | **仅 ens18**（bc:24:11:1a:8f:43）；ens19 已被用户在 PVE 中移除                                  | 见 §5.2「单网口起步」     |

### 关键结论

1. 环境已回归**近乎白纸**状态，无需再做"接管旧系统"的复杂动作，可按最优架构直接构建。
2. **RealVNC 商业版已就位且在跑** —— 这从"待办风险项"变为"必须保护的既有资产"：  
   任何操作都不得破坏 X 会话、LightDM 与 5900 监听。
3. 只有 **1 个物理网卡**，因此第一阶段（构建期）网络拓扑为  
   **ens18 = LAN + 管理口**，WAN 待用户在 PVE 加卡后再绑定。

## 二、优化后的完整需求规格（可直接作为提示词）

### 0. 总体架构与约束

- 底座：Debian 13（trixie），SeaBIOS 传统引导，保留 XFCE + Xorg + LightDM。
- 架构：**原生服务承担协议逻辑 + 轻量 Web 管理端只做配置生成/下发/观测**。  
  Web 端不重新实现 PPPoE、DHCP、RA、NAT 等协议，只负责生成各服务的原生配置文件并 reload。
- 资源约束（2C/3.8G）：Web 后端使用 **Python 3 标准库**（http.server + ssl + sqlite3），  
  不引入 Flask/FastAPI/Node/gunicorn；常驻内存目标 < 25 MB。
- 前端：原生 HTML + CSS + Vanilla JS，无构建步骤、无 npm 依赖。
- 模块化：每个功能一个独立页面，页面右下角固定 **"保存并应用"** 操作栏，  
  具备：语法/配置预检 → 备份快照 → 应用 → 结果提示（简体中文）→ 可回滚。
- 持久化：SQLite 保存 Web 层配置（网卡备注/角色、WAN/LAN、DHCP Options、管理员账户、审计）。  
  **SQLite 不作为唯一配置源**：每次应用都会渲染出原生配置文件落盘，系统重启后以原生配置为准。

### 1. 用户与登录体系（两套分离）

- **Web 管理员**：存 SQLite，PBKDF2-HMAC-SHA256 加盐哈希；独立于 Linux 用户；可改密码。
- **Debian 系统用户**：Web 可增删系统用户、修改密码、禁用/启用；用于 SSH 登录。
- **SSH 公钥**：支持粘贴文本与上传 .pub 文件两种写入方式，写入对应用户 `~/.ssh/authorized_keys`，  
  属主/权限强制修正为 `owner:user 600`，`.ssh` 目录 `700`。**明确禁止上传私钥。**
- **root 策略**：SSH `PermitRootLogin no` 保持不变；本地控制台/串口保留 root 应急登录。
- 所有用户管理操作写入审计日志。

### 2. 网卡管理（MAC 为主键）

- 以 **MAC 地址** 作为接口唯一标识，网卡名（ens18/ens19/enpXsY）仅作为当前显示值。  
  硬件变更导致改名后，仍能按 MAC 恢复角色与备注。
- 字段：MAC、当前名称、备注（如"电信光猫"/"客厅交换"）、角色（WAN / LAN / 未分配）、  
  链路状态、速率、MTU、驱动。
- 支持**桥接**：将多个"未分配/LAN"口加入一个 bridge（br0），显示从属接口清单。
- **新增网卡监测**：每次页面加载与定时轮询时比对 MAC 集合，出现未知 MAC 时  
  在页面顶部弹出"检测到 N 个新网卡，请分类"提示条。
- 提供"硬件变更后的重新识别/修复"流程：按 MAC 重新绑定旧配置到新网卡名。

### 3. WAN 口

- 模式：PPPoE / DHCP(自动) / 静态，支持**一键切换**（需确认，会断网）。
- PPPoE：账号密码、服务名（可空）、MTU/MRU（默认 1492）、按需拨号/自动重连、  
  断线自动重拨、在线时长统计、默认路由、usepeerdns。
- 运营商适配（中国电信 / 中国联通 / 中国移动 / 中国广电）提供模板，主要差异在于  
  MTU、服务名、认证方式（PAP/CHAP/MS-CHAP）。**必须明示实际兼容性取决于运营商与线路，需实测。**
- 显示：连接状态、IPv4 地址、网关、DNS、MTU、TX/RX 实时速率与累计流量、在线时长。
- TX/RX 速率：直接轮询 `/sys/class/net/<if>/statistics/{rx,tx}_bytes` 计算差值，**零额外依赖**。
- ⚠️ **初始部署阶段只保存凭据、不自动拨号**，由用户确认后再触发切换。

### 4. LAN 口

- 支持网口桥接（br0），桥的从属口可视化增删。
- LAN IPv4 地址/掩码可编辑（当前 192.168.7.1/24）。
- 显示当前 LAN 地址、地址池规划、已分配租约（切换后）。

### 5. DHCP Server（RouterOS 风格 Options）

- 引擎：dnsmasq。
- 支持任意 DHCP Option Code 自定义：
  - code 3 = Gateway（路由器）
  - code 6 = DNS Server
  - 其他 code（如 43、121）自由添加，支持 `dhcp-option` 与 `dhcp-option-force`。
- 地址池范围、租期、静态绑定（按 MAC 固定 IP）。
- **输入校验**：IP 合法性、多个 DNS 用逗号分隔、非法 code 拦截，防止生成坏配置。
- 应用前 `dnsmasq --test` 语法校验。
- ⚠️ **初始阶段默认不启动**，避免与现有网络中的 DHCP 冲突造成地址风暴。

### 6. 防火墙（nftables）

- IPv4 与 IPv6 **分页面**展示与编辑，底层分别落到 `ip drouter4` / `ip6 drouter6` 表。  
  （刻意避开 docker 占用的 `ip filter` / `ip nat` 表名，见 §5.2）
- 提供"规则编辑文本框"供高级用户直接编辑，支持 `nft -c -f` 语法预检。
- 应用前自动快照，应用失败或 60 秒确认窗口内失联则**自动回滚**。
- 内置常用能力：NAT 伪装（masquerade）、端口映射、MSS clamp（PPPoE 必备）、  
  基础防入站、转发策略开关。

### 7. IPv6 完整功能

- 区分并分别展示：**WAN 地址获取 / DHCPv6 / 前缀委派 PD / LAN RA / LAN 地址池**。
- DHCPv6-PD 客户端：dhcpcd-base（`/etc/dhcpcd.conf`），显示是否拿到 PD 前缀。
- RA：radvd（`/etc/radvd.conf`），可调 RA 间隔、生命周期、M/O 标志、RDNSS、DNSSL。
- ND 参数：可调 `/proc/sys/net/ipv6/conf/*/` 下的 `ra`、`forwarding`、`mtu`、`accept_ra`、  
  `dad_transmits` 等；提供 ndppd 选项（仅在 ISP 需要 ND 代理时）。
- POOL 池可视化 + 备注（如"电信 /56"）。
- **不假设任何运营商一定下发 PD**，页面必须明确区分"有链路地址"与"拿到可分配前缀"。

### 8. DNS Server

- 引擎：dnsmasq。
- 三种上游来源可组合：① 继承 PPPoE/运营商下发 DNS（usepeerdns 生成的文件）  
  ② 自定义公共 DNS（223.5.5.5 / 119.29.29.29 / 114.114.114.114 / 8.8.8.8 等）  
  ③ 内网 DNS 服务器 IP。
- 支持 DNS 查询日志开关（默认关闭以省资源）。
- ⚠️ 初始阶段不抢占 53 端口。

### 9. UPnP

- miniupnpd：开/关、指定 WAN 口与 LAN 监听接口。
- **默认不得在 WAN 侧开放**，页面提供当前映射表查看。
- 生成配置只允许出现 miniupnpd 2.3.x 认识的选项（`ext_ifname` / `listening_ip`(网卡名) /  
  `http_port` / `enable_upnp` / `enable_natpmp` / `secure_mode` / `upnp_forward_chain` /  
  `upnp_nat_chain` / `upnp_nat_postrouting_chain` / `system_uptime` / `lease_file` / `uuid`）  
  以及 `allow`/`deny` 权限规则。
- ⚠️ `upnp_nat_prerouting_chain` 在 2.3.x **不存在**，写入会导致服务启动失败（已修正）。
- 两项开关（`enable_upnp` / `enable_natpmp`）都关闭时，进程正常退出（`Why did you run me anyway?`），  
  此时 `systemctl is-active` 为 `inactive` 属**预期状态**。

### 10. NTP Client

- chrony：自定义 server 地址列表；显示同步状态（已同步/未同步/偏移量/层级）。

### 11. 诊断工具集

- Ping（`iputils-ping`）、Traceroute / MTR（`mtr-tiny`）、  
  iperf3（内网吞吐）、互联网测速（HTTP 下载测速，不依赖外部 CLI）、  
  接口状态、连接数（`conntrack`）、抓包入口（`tcpdump`，限定包数与时长）。
- 所有命令**参数白名单校验**，禁止任意 shell 拼接。

### 12. 日志

- 统一结构化 JSONL：`{ts, level, module, code, msg_cn, msg_en, detail}`，  
  落盘 `/var/log/drouter/`，按模块分割（system/network/dhcp/dns/firewall/ipv6/pppoe/web）。
- 页面按模块过滤、关键字搜索、导出（JSON/文本）。
- **所有面向用户的提示、警告、错误以简体中文显示**，同时保留原始英文错误原文便于 AI 诊断。
- 同时提供 systemd journal 的聚合查看。

### 13. 电源与系统

- 安全重启（`systemctl reboot`）、安全关机（`systemctl poweroff`）、  
  强制重启（受二次确认保护，走 sysrq）。
- 可选定时重启。
- Web 操作审计：谁、何时、改了什么、是否成功。

### 14. 升级与桌面保护（RealVNC 相关）

- **反对"长期冻结大批系统包"的做法**：那会错过安全补丁，且 Debian 13 的 `apt upgrade`  
  不会无故删除 XFCE。
- 正确做法：
  1. Web 内"系统更新"模块默认只做 `apt update` + **列出待升级清单**，不做无人值守升级；
  2. 自动把 `xserver-xorg*`、`linux-image-*`、`xfce4*`、`realvnc*` 标记为 **高危变更**并高亮；
  3. 升级前强制创建配置快照；升级后提供"验证清单"（图形会话、VNC 连接、路由服务）；
  4. 仅当 RealVNC 官方明确要求固定版本时，才对**该包**单独 `apt-mark hold`，  
     提供开关而非默认全量 hold。

### 15. NAT 类型检测（自动）

- 纯 Python 标准库实现 STUN Binding Request（原始 UDP socket + `struct` 手工构包），  
  无需 `stun`/`pystun` 等第三方包。
- 多服务器交叉判定：`stun.miwifi.com` / `stun.chat.bilibili.com` / `stun.cloudflare.com`。
- 输出 `NAT1`（全锥形）/ `NAT2`（地址受限锥形）/ `NAT3`（端口受限锥形）/ `NAT4`（对称型）  
  及对应中文语义说明；结果缓存以便进入页面即时展示。
- 实现于 `act_nat_check`，web 路由 `/api/nat/check` + `/api/nat/last`。

### 16. nftables flowtable 软加速

- 生成 `table inet drouter_accel`：  
  `flowtable f { hook ingress priority 0; devices = {...} }`
  - `chain forward { ct state established,related flow add @f }`。
- **硬件卸载自动探测**：`_hw_offload_capable()` 逐网卡检查 `ethtool -k` 的 `hw-tc-offload`。
  - 支持 → 渲染带 `flags offload` 的 flowtable，并 `ethtool -K ... hw-tc-offload on`；
  - 不支持（典型：**virtio 网卡为 `off [fixed]`**）→ 渲染**纯软件 flowtable**。
  - `nft -c` 预检失败时自动降级为软件模式重试。
- 页面与 NAT 检测**同页**（概述 → 网络状态），显示开/关状态 + 8 项影响说明。
- 实现于 `act_accel`，web 路由 `/api/accel`（op = get/on/off）。

### 17. VLAN 与 WOL 唤醒

- **VLAN**（主要面向 IPTV）：支持在父接口上创建 802.1Q 子接口，内置运营商 IPTV 常见 VID 预设；  
  记录存 `settings.vlan`，落地 `/etc/drouter/generated/vlans.json`。
- **WOL**（网卡远程唤醒）：读取网卡 `supports_wol` / `wol_mode`（`ethtool`），  
  发送 magic packet（`etherwake` 或原生 socket），支持保存常用目标设备。
- 均归属「接口」父菜单（二层/物理口相关）。

### 18. Web 终端（受控 Shell）

- **非 PTY**：单命令 `/bin/sh -c` 执行，不做完整终端仿真 —— 安全优先。
- `SHELL_BLOCK` 危险命令黑名单（`rm -rf /`、`mkfs`、`dd of=/dev/*`、`shutdown`、`reboot` 等）
  - `_shell_check` 拦截。
- 前端支持：用户名密码登入、配置存 localStorage、私钥/公钥登入、导入导出（含密钥）到文件。
- 实现于 `act_webshell`，web 路由 `/api/webshell/*`。

### 19. 文件管理器

- 动作：`list` / `read` / `get` / `hash` / `mkdir` / `rename` / `delete` / `zip` / `write` / `search`。
- **三重安全边界**：
  1. `FS_ROOTS` 根目录白名单；
  2. `FS_DENY` 敏感路径拒绝；
  3. `realpath` 解析后二次校验（防软链绕过）。
- 删除进**回收站** `/var/lib/drouter/trash`（不直接 `unlink`）。
- 支持单文件下载、文件夹 zip 打包下载、带进度条上传。
- 实现于 `act_fs`，web 路由 `/api/files*`。

### 20. 运行依赖自检与一键安装

- 35 项依赖清单，`_dep_installed` 支持 `'a|b'` **别名匹配**（如 `'vim|vim.tiny'`）。
- 一键安装日志落盘 `/var/log/drouter/dep-install.log`，失败时前端弹出**可复制**日志。
- 提供「再次检测」按钮；检测 `/usr` 只读并给出可操作提示。
- 实现于 `act_depcheck`，web 路由 `/api/deps/check|install|log`。

### 21. 通用外部 API

- `build_openapi(base)` → **OpenAPI 3.0.3** 描述文档（33 个路径）。
- `build_examples(base)` → **9 语言范例**：curl / python / javascript / go / java / php / shell / powershell / http。
- 设计目标：**零依赖接入** —— 任何语言只要能发 HTTP + `Authorization: Bearer <token>` 即可调用。
- 路由：`/api/openapi`、`/api/openapi.json`、`/api/examples`；前端「工具 → API」页面可切换语言并一键复制。

### 22. 虚拟化环境感知

- `_detect_virt()`：读 `/sys/class/dmi/id/sys_vendor` + `/sys/class/dmi/id/product_name`
  - `/proc/cpuinfo` hypervisor 标志，`systemd-detect-virt` 兜底；  
    比对 `_VIRT_SIGNATURES`（proxmox/qemu/kvm/vmware/hyperv/xen/virtualbox/parallels/bochs/cloud）。
- `_VIRT_PASSTHRU` 给出各平台**硬件直通建议**（含"不保证成功"的诚实提示）。
- 用途：温度传感器缺失时给出准确原因（虚拟机无法读取物理传感器），  
  前端以 ⚠ 惊叹号 + 说明文案呈现；主机信息卡新增「运行平台」。

### 23. PPPoE 多拨（对标爱快「多拨」）

- **目标**：在同一物理 WAN 口上并发 N 条 PPPoE 会话，聚合带宽并做负载均衡 / 主备切换。
- **实现要点（缺一不可）**：
  1. 每条会话是一张独立 ppp 接口 `drouter-wan1..N`，由独立 systemd 单元  
     `drouter-pppoe@i.service` 管理（`pppd call <peer> nodetach`）；
  2. 每条会话绑定**独立路由表** `100+i`；
  3. **基于源地址的策略路由**（`ip rule from <本端IP> lookup 100+i` + `ip rule fwmark 1000+i`）  
     —— 这是多拨能工作的关键：没有它会出现「A 会话出去的包从 B 会话回来」导致连接重置；
  4. 三种负载策略：
     - `balance`：加权 ECMP，所有会话同时承载；
     - `primary_backup`：只用第一条，主链路断开自动切备用；
     - `weighted`：按每会话 `weight` 分配（如 500M+500M+200M → 5:5:2）。
- **钩子**：`/etc/ppp/ip-up.d/drouter-pppm-route` 与 `ip-down.d/` 对应脚本，  
  在拨通/断开时自动挂接或清理路由表与 ip rule。
- **账号存储**：`/etc/drouter/generated/pppoe-multi.json`（0600，含密码）；  
  凭据以 `include` 方式写入 `/etc/ppp/chap-secrets.drouter-multi`（0600），  
  **不覆盖**用户原有 `chap-secrets` 内容。
- **安全**：`apply` 需 `confirm=true` 且 BUILD_MODE 关闭；密码**永不回传前端**，  
  前端只拿到 `has_password` 布尔值；密码留空表示沿用旧值。
- 实现于 `act_pppoe_multi`，web 路由 `/api/pppoe-multi`、`/api/pppoe-multi/log`。
- 菜单位置：**接口 → PPPoE 多拨**（紧跟 WAN 口之后）。

### 24. QoS 智能限速（对标爱快「智能流控」）

- **四层能力，按「先简单后复杂」组织**：
  1. **CAKE 智能整形**（默认）：上行直接挂 WAN 出口  
     `tc qdisc replace dev $WAN root cake bandwidth <up>Mbit nat dual-srchost <mode>`；  
     下行**必须走 IFB 重定向**（入口流量无法直接排队）：  
     `tc qdisc replace dev $WAN handle ffff: ingress` +  
     `tc filter replace dev $WAN parent ffff: protocol all matchall action mirred egress redirect dev ifb-drouter`  
     再在 IFB 上 `tc qdisc replace dev ifb-drouter root cake ... nat dual-dsthost <mode>`；
  2. **HTB 按 IP 精确限速**（填了 IP 规则则启用，与 CAKE 互斥）：  
     WAN 与 IFB 各建同构 HTB 树，nft `meta mark set 0x100x` 打标，  
     `tc filter ... handle 0x100x fw flowid 1:1x` 分类；每类挂 `fq_codel`；
  3. **DSCP 打标**：4 个预置（游戏 cs4 / 语音 ef / DNS ef / BT cs1），  
     链 `dscp` 在 `priority mangle`，双向按端口打标；
  4. **nftables 连接数限制**：`ct state new ct count over <N> counter drop`。
- **CAKE 三档模式**：`diffserv3`（推荐）/ `diffserv4` / `besteffort`。
- **⚠ 与 flowtable 软加速冲突**：flowtable 让已建立连接绕过 netfilter 钩子，  
  导致 DSCP 打标与 mark 分类失效。`get` 返回 `accel_conflict` 主动提示，  
  `on` 会拦截并要求用户先关闭软加速（或显式 `ignore_accel=true`）。
- **幂等性**：脚本内先用 `tc qdisc replace`（replace 语义）+ 加载 nft 前  
  `nft delete table inet drouter_qos`，可重复执行不叠加规则。
- 关键常量：`QOS_IFB='ifb-drouter'`、`QOS_MARK_BASE=0x1000`。
- 实现于 `act_qos`，web 路由 `/api/qos`。
- 菜单位置：**服务 → QoS 智能限速**（服务组首位）。


### 25. DPI 识别库 + 多前缀代理更新
- **用途**：按应用/协议识别流量（爱快的杀手锏）。Debian 上对应 nDPI / Suricata。
- **痛点**：nDPI 规则库与源码都在 GitHub，国内直连常常超时或极慢。
- **方案：7 个内置加速前缀 + 自定义**：
  `direct` / `ghproxy` / `gh-proxy` / `moeyy` / `ghfast` / `ghproxy-net` / `gitclone`
  （`gitclone` 是整站镜像，URL 拼接规则与其他不同，代码内已单独处理）。
- **测速优选**：`_dpi_test_mirror` 对候选前缀做**限时 4s + 限速 16KB/s** 的
  连通性测试，只要在时限内拿到 >=1 字节且 HTTP 2xx 即判可用，按耗时升序返回。
  > **实测踩坑**：起初用 `curl -r 0-0`（Range 取 1 字节）测速，结果**多数公共加速会忽略
  > Range 头**，直接开始传整个 46MB 包 → 必然超时，产生假阴性。改用「限时+限速+看是否
  > 收到数据」后结果才与真实下载能力一致。另外 gitclone / gh-proxy 等**不代理
  > `codeload.github.com`**，测速 URL 必须与真正下载的 URL 同形。
- **三个来源**（可分别更新）：
  - `ndpi-protos`（ntop/nDPI，archive）→ `/opt/drouter/dpi/ndpi`
  - `suricata-rules`（OISF/suricata-update，archive）→ `/opt/drouter/dpi/suricata-update`
  - `ndpi-netfilter`（ndpi-netfilter/ndpi-netfilter，archive）→ `/opt/drouter/dpi/ndpi-netfilter`
- **原子安装**：下载 → 解包到私有临时目录 → 旧版本改名为 `.old` → 移入 `target` → 清理。
  解包失败不会破坏旧版本。
- **安装建议（plan，不真正执行 apt）**：`apt` / `source`（源码编译）/ `netfilter`（内核模块）
  三条路径，各自生成可复制到 Web 终端的命令。
- **状态与日志**：`/opt/drouter/dpi/state.json`（记录 last_mirror / last_update / results）；
  日志落盘 `/var/log/drouter/dpi-update.log`。
- 实现于 `act_dpi`，web 路由 `/api/dpi`、`/api/dpi/log`。
- 菜单位置：**服务 → DPI 识别库**（紧接 QoS 之后）。

### 25.1 helper 私有临时目录（跨模块基础设施）
- **背景**：`/tmp` 与 `/var/tmp` 带 sticky 位（`drwxrwxrwt`）。内核默认
  `fs.protected_regular=2` 时，**root 也会被禁止覆写「不属于自己的已存在文件」**。
  历史版本若以低权用户（`drouter`）在 `/var/tmp` 留下过同名文件，后续 root 写入
  会**永久报 `Permission denied`** 而卡死（本项目的 QoS 首次就该坑失败）。
- **对策**：统一改用 `/run/drouter-helper/`（tmpfs，重启自清，root 独占 0700），
  文件名带 `pid + 毫秒时间戳` 保证唯一。辅助函数 `tmp_nft_path(tag)` /
  `write_tmp_nft(tag, text)` / `cleanup_tmp(*paths)`。
- **影响范围**：QoS 规则预检、flowtable 加速预检、`_verify()` 通用配置预检、
  DPI 下载解包工作目录，均已迁移。
- 部署脚本 `deploy.sh` 会 `mkdir -p /run/drouter-helper && chmod 700`。

### 25.2 nft 语法与预检的两个坑（实测记录）
- **`nft -c` 需要 netlink 缓存权限**：在受限沙箱/低权环境报
  `cache initialization failed: Operation not permitted`。这不是规则语法错误。
  **对策**：`_nft_environ_blocked()` 识别该特征后**降级为「影子表真实加载校验」**
  —— 把表名换成 `<table>_check` 生成一份规则真实 `nft -f` 加载，校验通过后立刻删除，
  既不污染生产表，又能完整验证语法与表达式合法性。
- **nft 保留字与 priority 表达式**：
  - 链名不能叫 `mark`（保留字）→ 报 `syntax error, unexpected mark`，改用 `marking`；
  - `priority mangle + 1` **非法**（priority 不支持算术）→ 必须写数值，
    本项目的标记链用 `priority -149`（mangle=-150 之后 1 位）；
  - `chain` 块内每条规则末尾**必须带分号**，漏写报
    `syntax error, unexpected '}', expecting newline or semicolon`。
- **`nft -f` 是追加语义**：重复 `nft -f` 同一文件会把规则叠成两遍。
  **对策**：加载前先 `nft delete table inet <name>`（幂等）。

### 25.3 新手向导（#84）—— 为什么单开一个页面而不是把既有页面做简单点

- **菜单位置**：**概览 → 新手向导**（概览组第一位，`needSave: false`）。
  新手打开后台第一眼就该看见它；放进系统组或工具组要先知道去哪找，就失去意义了。
- **职责边界**：向导**不新增任何配置能力**，它只是把既有模块（`ppp` / `dnsmasq` /
  `chrony` / `radvd` / `nft_v4`）的必填项挑出来，套上范例与体检。所有写盘仍走
  `act_apply('live': True)` 这条唯一通道 —— 向导里**没有第二套落盘逻辑**。
- **后端**：`act_wizard`（`op` = `probe` / `apply_step` / `dial`）。纯函数
  `_wiz_ip_in_pool` / `_wiz_same_subnet` / `_wiz_local_ipv4` / `_wiz_ping` /
  `_wiz_dns_probe` / `_wiz_has_ipv6_global` 全部可在隔离命名空间里单测。
- **前端**：`viewWizard` 等 18 个函数；四步是可点按钮而非进度指示器
  （用户可以任意顺序回头补第 2 步）。
- **两条硬规则**（写进代码注释，改代码时别踩回去）：
  1. **地址池校验按数值比**：`'192.168.1.9' > '192.168.1.100'` 字符串比是 True，
     按字符串比会把合法地址池判成非法。
  2. **第 4 步前缀强制 `/64`**：RFC 4862 规定 RA 通告前缀长度必须为 64；
     用户填 `/80` 自动规范化并说明原因，关闭 IPv6 时**保留前缀不删**。
- **半成功不回滚**：四步里某步失败时，前面已成功的步骤保持生效。
  新手最怕的是「点了个按钮，全没了」。
- **拨号必须二次确认**：`dial` 是独立动作（保存 ≠ 拨号），要手打「拨号」两个字，
  页面明示「会短暂中断现有网络」。
- **验收脚本刻意不真拨号**：`_dev/live-wizard.py` 只验参数校验，
  真拨号会改默认路由 —— 触碰「不接管路由」这条红线。
- 单测 `_dev/t-wizard.py`（160 项）+ 真机 `_dev/live-wizard.py`（75 项）全过；
  单测已挂进 `devtools/sync.sh` 预检链。

## 五、三个关键前提的处置决策

### 5.1 RealVNC 商业版已运行 —— 必须保护（最高优先级）
实测：`realvnc-vnc-server 6.11.0.47988` 已安装，`vncserver-x11-serviced.service` active，
TCP/UDP 5900 正在监听。

**保护策略（贯穿全项目）：**
1. 本系统**不接管、不重启、不配置** VNC；只做"只读状态展示 + 升级影响预警"。
2. **不断言"必须冻结桌面包"**：Debian 13 的 `apt upgrade` 不会无故移除 XFCE。
   正确做法是升级前快照 + 升级后验证清单（见 §14）。
3. Web 的"系统更新"模块**默认只列清单不执行**，并对以下包高亮标记为高危：
   `xserver-xorg*`、`xorg`、`linux-image-*`、`linux-headers-*`、`xfce4*`、`realvnc*`、`vnc*`。
4. 仅在 RealVNC 官方明确要求固定版本时，才对该**单个包**执行 `apt-mark hold`（提供开关，不默认全量 hold）。
5. 所有网络/防火墙变更**必须**走"快照 → 应用 → 倒计时确认 → 自动回滚"，避免把 VNC 会话一起弄断。
6. Web 管理端监听端口与 5900 隔离，且默认不允许在 WAN 侧访问。

### 5.2 单网口起步（当前阶段）
用户当前只给 ens18 一个口，WAN 口待后续在 PVE 添加。
- **构建期配置**：ens18 = LAN，承载 192.168.7.3/24（**保持 DHCP 获取，先不动**，避免失联）。
- **WAN 口状态**：暂记为"未分配"，Web 页面显示提示
  "未检测到独立 WAN 口，请在 PVE 添加网卡后于网卡页分配角色"。
- **WAN 相关服务**（pppd / dhcpcd / NAT）在无 WAN 口时**只生成配置、不启动**。
- 后续加卡后：新网卡以 **MAC 为键**自动出现在"待分类"提示条中 → 一键指派为 WAN。
- **网桥**：单口阶段无剩余口可桥接，功能保留但不启用，页面给出说明。

### 5.3 NetworkManager → systemd-networkd 迁移（改为"可选"）
原方案要求迁移，理由是 NM 与 networkd 会互相打架。但考虑到：
- RealVNC 依赖稳定的网络与图形会话，迁移过程**必然中断网络**；
- 当前只有一个网口，一旦迁移失败可能直接失联（需 PVE 控制台救回）。

**调整为：**
- **默认不迁移**。后端统一通过 **NetworkManager（nmcli）** 管理 ens18，前端屏蔽底层差异，
  功能上与 networkd 方案等价。
- 提供"高级 → 网络后端迁移"入口，做 **dry-run 预览**（展示将写入的 `.network` 文件），
  由用户在有 PVE 控制台可救回时自行决定是否执行；执行前强制快照。
- 若未来网卡数量增多、配置复杂化，再考虑迁移。

> 说明：NM 与 networkd 二选一，**绝不并行管理同一张网卡**（单一管理者原则仍成立）。

## 七、权限模型

1. 后端进程以专用低权用户 `drouter` 运行，**不以 root 运行**。
2. 需要 root 的操作一律通过 `sudo -n /opt/drouter/bin/drouter-helper <action> '<json>'`。
3. sudoers 仅放行这一个脚本（NOPASSWD），脚本内部维护 **action 白名单**，
   并对每个参数做类型/正则/取值范围校验，杜绝 shell 拼接。
4. Web 端：HTTPS(8443，自签证书) + 登录会话 + CSRF token + 登录失败限速 + 会话超时。
5. 管理页默认仅监听 LAN 地址；提供"允许 WAN 侧访问"开关，默认关闭。

```
   3. 快照当前配置 → snapshots/<ts>
   4. 原子写入新配置
   5. reload / restart 目标服务
   6. 健康探测
   7a. 成功 → 中文提示"已应用"，进入 60s 确认窗口
   7b. 失败或超时未确认 → 自动恢复快照并提示
```
- 网络类变更（WAN 模式、桥接、PPPoE、networkd 迁移）标记为 **高危**，二次确认 + 倒计时。
- 防火墙变更应用失败绝不破坏已有有效规则。

## 十、必须在目标环境实测验证的事项

1. **PPPoE 拨号**：所属运营商的认证方式（PAP/CHAP）、服务名是否需要、MTU 是否需 1492。
2. **IPv6 PD**：是否真的下发前缀（有链路地址 ≠ 拿到 PD）。
3. **桥接后网卡关系**：目前只有 2 个物理口，扩展网卡后需验证。
4. **RealVNC 在 Debian 13 + XFCE 上的兼容性**：官方支持矩阵为准。
5. **MTU/MSS clamp**：PPPoE 下的实际路径 MTU。
6. **docker 停用后**业务是否受影响。

## 十二、切换策略（针对"局域网正在运行"的约束）

> 环境已还原为干净状态，旧系统不存在，因此不再需要"接管旧系统"。
> 但 **局域网仍在运行**，且 **RealVNC 会话不能断**，约束依然生效。

1. **构建期（当前）**：
   - 只装包、只写配置、只建 Web；
   - **不启动** dnsmasq / radvd / dhcpcd / miniupnpd 抢占端口（53/67/546/5353）；
   - **不拨号**、**不改 ens18 现有 IP（继续 DHCP 获取 192.168.7.3）**、**不停 NetworkManager**；
   - **不写 nftables 生效规则**（可生成、可预检，不加载）；
   - **不触碰 RealVNC / LightDM / X 会话**。
2. **准备期**：Web 内填好 PPPoE 账号密码、LAN 规划、DHCP 池、Options、防火墙规则 → 全部只保存。
3. **加 WAN 口**：用户在 PVE 为 102 添加第二张网卡 →
   Web 网卡页按 MAC 自动识别 → 指派为 WAN → 后端按 MAC 生成绑卡规则。
4. **切换窗口（需你明确确认后再执行）**：
   `应用 LAN 静态地址 → 启动 dnsmasq → 应用 nftables → 启动 PPPoE 拨号 → 启动 radvd/dhcpcd`。
   每步带快照与自动回滚；网络类变更带 60s 倒计时二次确认。
5. **验证期**：确认上网 / IPv6 / DHCP / DNS 正常，且 RealVNC 5900 连接未受影响。
6. 任一步失败 → 一键回滚至快照。
